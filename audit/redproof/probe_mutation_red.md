## Findings about the probes

- probe_schema_namespace_resolution and probe_split_namespace are VACUOUS for their stated claim. With the namespace check (store.py:148) or the split check (store.py:175) disabled, both still print VERDICT: PASS. Their shadow table `public.events (id int)` lacks `commit_xid`, so the column-completeness check refuses it. On 433f187 the refusal text is the namespace one; on the mutant it is `events.commit_xid is missing`. Neither probe asserts which check refused. The fix belongs in the probe: give the shadow the full column set, or assert on the refusal text.
- probe_heartbeat_survives_blip is VACUOUS for its stated fault, one failed renewal. A mutant whose heartbeat stops for good after the first failure stayed green on SQLite and PostgreSQL in two separate runs. With the heartbeat disabled entirely, the probe went red once, and only on the postgres CONTROL case (executions=2). Postgres case A and both SQLite cases still read executions=1. The duplicate depends on timing, and the SQLite leg never showed one. The probe cannot currently tell a heartbeat that survives a blip from one that dies at the first blip.
- probe_event_store_ddl_on_construction is VACUOUS. It prints `PROBE CONCLUSIVE: both directions observed.` and exits 0 on two opposite contracts: a constructor that always issues DDL (mutant) and one that never does (433f187). It is already excluded from run_all.sh as historical, so it gives no coverage.
- probe_ssrf_rebinding goes red under the connect-time-guard mutant, but for the wrong reason: `>>> FAIL: connection did not succeed, but not via the SSRF guard`. Its leak detector reads `result.context`, while HTTPTask puts the body in `result.outputs`. So the `rebinding succeeded, the private service was read` branch cannot fire: the mutant's task reached the internal service (status SUCCEEDED) and the probe reported it as a non-connection. It still exits 1, and its fallback branch is what saves it.
- probe_circuit_storage_honesty goes red when the degradation is silent and strict mode is disabled. It does not verify the log level it claims ("say so at ERROR"): a DEBUG-level message passes, because the capture handler has no formatter and the filter matches the word `unavailable`.
- probe_signal_storage_degrades: under a mutant that always reports storage usable, the check `workflow succeeds without the grant` stayed PASS (the probe went red on two other checks). That check alone does not exercise the InsufficientPrivilege death path it describes.
- Defence-in-depth observation, not a probe defect: probe_two_processes_execute_once went red as soon as the queue claim fence was removed (the SQLite version predicate and PostgreSQL FOR UPDATE SKIP LOCKED). On both backends nothing else (dedup, store versioning) stopped duplicate task execution.
