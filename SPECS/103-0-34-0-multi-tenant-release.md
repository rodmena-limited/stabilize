### WI-2 tenant key and tenancy mode — slice 1 (column, mode record, API)

- When a SQLite engine file (store, queue incl. custom queue tables and their `_dlq` siblings, event store, task leases, signals) is first opened by 0.34, stabilize shall add the tenant column to every engine-shaped table that lacks it and seed the mode record, in one `BEGIN IMMEDIATE` transaction.
- Every store, queue and event store constructor on both backends shall accept `tenant` matching `^[A-Za-z0-9.:-]{1,64}$` or `''`; if `tenant` is `None` or malformed, then the constructor shall raise `TenantError`.

The engine shall never default the mode.
- Every engine borrow of a `PostgresWorkflowStore` or `PostgresQueue`, including the module-level functions in `postgres/queries.py`, `postgres/operations.py` and `queue/dlq.py` and the `TaskLeaseManager`, shall pass through the owner's `_borrow()` (they receive an `EngineBorrower`, never the pool); `tests/test_tenant_api.py` calls every public operation under a refused tenant and expects `TenancyModeError` from each.
- When a `PostgresEventStore` is constructed, it shall verify its schema and read the mode record (it connected at construction before 0.34 and keeps doing so).
- `is_healthy()` shall answer reachability only and shall not read the mode record.
- While a schema is in single-tenant mode, constructing with a non-empty tenant shall raise `TenancyModeError`; while in tenancy mode, constructing with `''` shall raise `TenancyModeError`.
- If `QueueProcessor`, `Orchestrator` or `store.transaction(queue)` receives parts whose `tenant` attributes differ, then it shall raise `TenantError` before any other work.
- `PoolOptions` shall accept `tenant_setting` (matching `^[a-z_][a-z0-9_]*\.[a-z_][a-z0-9_]*$`, never the `stabilize.` class) and `audit_key: bytes`; `PoolOptions.key()` shall cover every dataclass field.
- `PostgresEventStore(create_tables=True)` shall create the three event tables with the tenant column plus the mode table and its seed; `setup_ddl()` shall contain the same DDL; `PostgresEventStore` shall apply `with_schema` to its pool options.
- If the target schema of `mg-up` is named after the connecting role while `"$user"` is on the search_path, then `mg-up` shall refuse with `TakeoverRefusedError` before any change (B65).

### WI-2 slice 3: tenancy-mode CLI and tenant-scoped statements (done)
- `stabilize mg-tenancy status` shall print the mode, `enabled_at` and `enabled_by` of the target schema.
- `stabilize mg-tenancy enable` shall take mg-up's advisory lock, require every shipped migration applied, require zero rows in every engine table and in every custom queue table named by `pipeline_executions.queue_table`, and shall then set `stabilize_tenancy` to `(mode = 'tenancy', enabled_at = now(), enabled_by = current_user)` in one transaction. It shall print that every engine process must be stopped first (rule 2).
- `stabilize mg-tenancy disable` shall have the same preconditions and set the mode back to `single`.
- If any precondition fails, `mg-tenancy enable|disable` shall exit 1, name the failing table or migration, and change nothing.
- Every INSERT into an engine table shall set `stabilize_tenant` to the constructing part's tenant, on both backends.
- Every SELECT, UPDATE and DELETE on an engine table, including subqueries, CTE arms and the queue poll, shall carry `stabilize_tenant = <tenant>` as a bound parameter; module-level functions take the tenant from the `EngineBorrower` they receive.
- When an insert conflicts with a row the caller cannot see (another tenant's), the engine shall raise `TenantMismatchError`; a conflict with a visible row keeps its usual contention result (rule 4).
- While a schema is in tenancy mode, a part constructed for tenant A shall observe none of tenant B's rows through any public operation; `tests/test_tenant_isolation.py` enumerates the operations on PostgreSQL, and on SQLite through two processes sharing one file.
- The SQLite `ConnectionManager` shall refuse a second tenant on the same file within one process (`:memory:` exempt).
- The monitor shall accept `--tenant` and `--all-tenants`; while the schema is in tenancy mode, one of them shall be required.
- `stabilize mg-tenancy` shall accept a `sqlite:///` URL and switch the file's mode record under the same empty-file rule.
- B66 (found by this slice's live run): the PostgreSQL processed-message retention batch shall delete at most `batch_size` rows per statement and at most `max_rows` per call, whatever the plan and however `processed_at` ties (`tests/test_audit_retention.py::test_cleanup_never_deletes_past_max_rows_when_timestamps_tie`).

- Slice 4 adds the GUC checks, the FORCE RLS refusal, the CHECK constraint, the fence, the default drop and the `TenancyModeChanged` latch.

### WI-2 slice 4: the PostgreSQL fence and the armed borrow path (done)
- Every engine borrow of a PostgreSQL store, queue or event store shall run, as its first statement, `SELECT set_config('stabilize.tenant', <tenant>, true) WHERE coalesce(current_setting('stabilize.tenant', true), '') = ''`; if that statement returns no row (the setting was already set on the connection), then the borrow shall raise `TenantContextError` naming the value found, and the connection shall go back to the pool.
- Where `PoolOptions.tenant_setting` is configured, the borrow shall refuse a current value of that setting outside `('', <tenant>)` with `TenantContextError`, and shall then set it transaction-locally to the tenant.
- When engine code commits or rolls back on a borrowed connection before the borrow ends, the connection shall re-arm both settings before the next statement (connection subclass; structural, not a list of call sites).
- If a borrowed connection is in autocommit mode, then the borrow shall refuse it with `TenantContextError`.
- `stabilize mg-tenancy enable` shall, in the one transaction that flips the mode, create the function `stabilize_tenant_fence()` (`SECURITY INVOKER`, `SET search_path = pg_catalog, pg_temp`) and a `BEFORE INSERT OR UPDATE OR DELETE FOR EACH ROW` trigger `stabilize_tenant_fence` on every engine table and every custom queue table, add the constraint `stabilize_tenant_nonempty CHECK (stabilize_tenant <> '')`, and drop the `''` default of `stabilize_tenant`.
- The fence shall raise SQLSTATE `ST001` when `current_setting('stabilize.tenant', true)` is null or `''`; `ST002` on INSERT when the setting differs from `NEW.stabilize_tenant`, on DELETE when it differs from `OLD.stabilize_tenant`, and on UPDATE when it differs from `OLD.stabilize_tenant` or `NEW.stabilize_tenant` differs from `OLD.stabilize_tenant`; and `ST003` when the setting is `'*'` and `pg_has_role(current_user, <table owner>, 'MEMBER')` is false. A setting of `'*'` held by an owner member passes.
- `stabilize mg-tenancy disable` shall drop the triggers, the function and the CHECK constraint and restore the `''` default in the same transaction as the mode flip.
- If any engine table has `relforcerowsecurity` set, then `mg-tenancy enable` shall refuse and name the tables and their policies.
- If `stabilize.tenant` is set for the database or any role (`pg_db_role_setting`), or is non-empty on a fresh connection, then `mg-tenancy enable` shall refuse and name where it is set.
- The engine shall map errors by SQLSTATE through one `sqlstate(exc)` helper: `ST001` to `TenancyModeChanged`, `ST002` to `TenantMismatchError`, `ST003` to `TenantPermissionError`; `23502` and `23514` map to `TenancyModeChanged` only when `diag.column_name` is `stabilize_tenant` or `diag.constraint_name` is `stabilize_tenant_nonempty`.
- The arm shall be one statement that also returns the mode record and its row-security flags, and the host setting's state when `tenant_setting` is configured; it shall run lazily before the first statement of a borrow and before the first statement after a commit or rollback inside the borrow (a commit that ends a borrow costs nothing).
- While the mode last read is `single`, is younger than 5 s and no `tenant_setting` is configured, the borrow shall run no arm (there is no fence to satisfy and the setting is unused); the mode is re-read, through the same statement, at most every 5 s. Measured cost: single-tenant mode unchanged within one statement per 5 s; tenancy mode one statement per engine transaction (one stage went from 87 to 135 statements in the budget test before the skip).
- Rule 6's "first statement of every engine transaction" is therefore read as "before the first statement, in tenancy mode or whenever a host setting is configured"; the decision is recorded here because the budget test showed a 55% statement increase for single-tenant installs that gain nothing from it.
- Slice 5 adds the `TenancyModeChanged` latch on the processor, the SQLite triggers and UDF, and the SQLite one-tenant-per-file refusal; slice 6 adds the first-use schema check, the indexes and the namespaced keys.

### WI-2 slice 5: the TenancyModeChanged latch and the SQLite fence (done)
- When any processor thread (poll loop, worker, recovery sweep, DLQ sweep, dedup hydration) meets `TenancyModeChanged`, the `QueueProcessor` shall record it as its fault, stop polling, let in-flight handlers finish, and shall neither ack nor reschedule the message whose handling raised it (the lease expires and another process, built for the new mode, picks it up).
- `QueueProcessor.fault` shall expose the recorded error; `stop()` shall log it; `start()` after a fault shall refuse with that error.
- The handler-level `except Exception` blocks in `complete_stage`, `start_stage` and `run_task` saving shall re-raise `TenancyModeChanged`, `TenantMismatchError` and `TenantContextError` before any transient/permanent classification; the signal mixin shall re-raise them too.
- On SQLite, `stabilize mg-tenancy enable` shall create, on every engine-shaped table, a BEFORE INSERT trigger that aborts with `ST001` when `NEW.stabilize_tenant` is `''` or NULL, and BEFORE INSERT, UPDATE and DELETE triggers that abort with `ST002` when the row's tenant differs from `stabilize_tenant()`, a function the `ConnectionManager` registers on every connection it opens; a connection bound to `'*'` passes. `disable` shall drop them.
- The `ConnectionManager` shall bind one tenant per SQLite file per process: the first part built for a file records its tenant, a later part with a different tenant is refused with `TenantError`, and `:memory:` is exempt. `stabilize_tenant()` returns the file's bound tenant.
- SQLite errors whose message starts with `ST001:` or `ST002:` shall map to `TenancyModeChanged` and `TenantMismatchError`; "no such function: stabilize_tenant" shall map to `TenantContextError` naming the unregistered connection.
- A tenancy-mode SQLite file is not writable from the `sqlite3` shell except by `DROP TRIGGER` (documented).

### WI-2 slice 6a: first-use schema check, tenant indexes, scoped locks, Workflow.tenant (done)
- On its first armed borrow, a PostgreSQL store, queue (its own table and `_dlq`) or event store shall read the catalog of the tables it uses and raise `EngineSchemaError` naming the exact DDL to run when: `stabilize_tenant` is missing, not `text`, nullable, or has a default that does not match the mode (`''` in single mode, none in tenancy mode); any column of its column lists is missing; or, in tenancy mode, the `stabilize_tenant_fence` trigger or the `stabilize_tenant_nonempty` constraint is missing on one of its tables. The check runs once per part per process; a part whose check failed refuses every later borrow with the same error.
- A SQLite store, queue or event store shall make the same check at construction against `PRAGMA table_info` and `sqlite_master`, in tenancy mode requiring the `stabilize_fence_del_<table>` trigger on each of its tables. On SQLite the `''` default stays in both modes (SQLite cannot drop a default without rebuilding the table; the `ST001` trigger refuses an empty tenant instead). Custom queue tables are checked against the `queue_messages` and `queue_messages_dlq` shapes. Because the engine owns SQLite DDL, a missing fence trigger on SQLite is recreated at first use (`ensure_tenant_schema`) rather than refused; the refusal covers columns and types. A PostgreSQL queue's check requires its `<table>_dlq` sibling to exist, because the dead-letter path writes there; `tests/test_retention_guard.py` creates both tables for its custom queue.
- A new migration shall add, `IF NOT EXISTS`, the indexes `(stabilize_tenant, deliver_at, locked_until, attempts)` and `(stabilize_tenant, attempts)` on `queue_messages`, `(stabilize_tenant, pipeline_config_id, status)` and `(stabilize_tenant, status)` on `pipeline_executions`, `(stabilize_tenant, status, id)` on `stage_executions`, `(stabilize_tenant, sequence)` and `(stabilize_tenant, coalesce(commit_xid, '0'::xid8), sequence)` on `events`, and `((payload ->> 'pipeline_config_id'))` on `queue_messages`; `mg-up` applies it and the schema-model test covers it.
- When the tenant is not `''`, `lock_admission(key)` shall take `pg_advisory_xact_lock(hashtextextended('admission' || chr(31) || tenant || chr(31) || key, 0))`; two tenants locking the same key shall not block each other; the `''` tenant keeps the two-integer key so a 0.33 process and a 0.34 process in single mode still exclude each other.
- `Workflow.tenant` shall be set from `stabilize_tenant` by both stores' row converters (the model has no `to_dict`, so the plan's `to_dict` clause does not apply); a workflow stored by a tenant-scoped store shall carry that tenant when read back.
- While a store's tenant is not `''`, `store()` shall refuse workflow, stage and task ids that are not 26-character Crockford ULIDs (`ValueError` naming the id), so ids cannot collide across tenants on the shared primary keys.
- `stabilize.current_tenant()` shall return the tenant of the store whose handler, task, hook or finalizer is running on the current thread, and `''` outside one; `RunTaskHandler` binds it around task execution.

### WI-3 message delivery correctness (rule 7) (done)
- Every handler transaction that pushes a message shall mark its delivered message processed in the same transaction; a mark that inserts no row shall raise `DuplicateDeliveryError` inside the transaction, and the transaction shall roll back.
- `process_and_ack` and `process_one` shall catch `DuplicateDeliveryError` and ack the redelivered message without an error context, a reschedule or a second mark; the handler `except Exception` blocks in `complete_stage`, `start_stage` and `run_task/saving` shall re-raise `DuplicateDeliveryError` ahead of `is_transient`.
- Exactly one marking transaction per delivery path: the bare `queue.push` sites in `start_stage/handler.py`, `start_stage/orchestration.py`, `start_workflow.py`, `start_stage/starting.py`, `complete_workflow.py` and `continue_parent_stage.py`, and the pushing transactions without marks in `complete_stage/handler.py`, `start_stage/handler.py` and `complete_stage/split_logic.py`, shall move into the transaction that marks the message.
- Both transaction classes shall record a `_pushed` flag when `push_message` runs and hand it to the committed-marks record on commit; after a handler returns, the processor shall treat a committed push without a committed mark as a defect: log at ERROR with the message type and id, count it in a metric, and ack the message (never raise after a committed push); under `STABILIZE_STRICT_DELIVERY=1` it shall raise instead. `NoOpTransaction` is exempt by name.
- `SignalStage` shall mark its message inside the transaction that stores the stage (today the mark runs after the connection is returned, on another thread's transaction at worst) (B05).
- `process_one` shall run its handler under the lock heartbeat so an overlapping cron drain does not execute a message twice (B15).
- `check_and_move_expired` shall move only rows whose lease has lapsed (`locked_until IS NULL OR locked_until < now()`), with `FOR UPDATE SKIP LOCKED` on PostgreSQL, on both backends (B16).
- One `sqlstate(exc)` helper (already in `persistence.tenancy`) shall serve `is_deadlock_error`, which shall keep {40001, 40P01} and stop depending on English error text (B31).
- A redelivered message whose mark is already committed shall be acked on both backends with `enable_deduplication=False` (pinned).
- The guard shall go green on a known positive: a handler that pushes on the queue's own connection records one `DeliveryDefect` naming the pushed type, and `process_all` under `STABILIZE_STRICT_DELIVERY=1` raises `DeliveryContractError` after acknowledging the message (`tests/test_delivery_marks.py::test_the_guard_flags_a_handler_that_pushes_outside_its_transaction`).
- The SQLite dead-letter sweep shall use the queue's `max_attempts`, the same rule as its poll, so a transactionally pushed row (stamped with the message default) is swept once the poll stops delivering it.

Synthesis deviations recorded while building WI-3:
- The strict flag raises at the end of `process_all`, after every message of the drain was acknowledged, never inside a delivery: a raise after a committed push would reschedule a message whose effects are already committed. `QueueProcessor.delivery_defects` (capped at 200) is the assertion surface; production logs ERROR and counts `stabilize.delivery.defects`.
- Bare pushes are recorded by `PostgresQueue.push` and `SqliteQueue.push` when no connection is passed. The named non-handler pushers wrap their pushes in `delivery_exempt()`: `Orchestrator`, `WorkflowRecovery`, `hitl.signal_stage`, `SynchronousProcessor.push_and_process`, `NoOpTransaction._flush_messages`.
- `check_and_move_expired` carries the lease predicate without `FOR UPDATE SKIP LOCKED`: its SELECT is a single autocommit statement, so the row lock would be released before the move; the predicate is what keeps a leased row out, and the poll's `attempts < max_attempts` keeps a swept row from being leased in between.

The completion moved to `complete_stage/fan_out.py::_complete_and_fan_out` and runs under `retry_on_concurrency_error`, re-reading downstream rows per attempt; the per-downstream five-attempt loop is gone.
- The deferred-choice sibling `CancelStage` messages join `messages_to_push` of the claiming `StartStage` (`_deferred_choice_sibling_messages`); WI-4 replaces them with `SkipStage(pruned=True)`.
- `DuplicateDeliveryError` is a `StabilizeError` in `stabilize.errors.delivery`, still importable from `stabilize.persistence.transaction`; `TransactionHelper.execute_atomic` no longer swallows it into `False` but lets it propagate to the processor, which acknowledges.

### WI-4 slice 4a: durable timers and the drain (done)
- `TimerTask` (a `RetryableTask`) shall read exactly one of `until` (ISO 8601 with offset, or epoch seconds) and `duration_seconds` (> 0) from the stage context; any other combination shall complete the task TERMINAL with the reason in `stage.context["exception"]`.
- On its first execution `TimerTask` shall write `_timer_armed_at` and `_timer_due_at` (epoch ms) to the stage context and return `TaskResult.running(scheduled_time=due)`; while the due time is ahead it shall return RUNNING with `scheduled_time=due` and a backoff of `due - now`; once `now >= due` it shall succeed. The due time is absolute: a pause does not move it.
- `TimerTask.get_dynamic_timeout(stage)` shall be `(due - armed_at) + grace` (grace 5 minutes), so a timer of any length is not cut by a fixed cap; the RunTask lifetime check shall exclude paused time (`_paused_ms`) for every `RetryableTask`.
- `PauseTask` shall record `_paused_at` and `ResumeStage` shall add the paused interval to `_paused_ms` and clear `_paused_at`.
- `WaitTask` shall be built on `TimerTask`: `waitTime` seconds, `waitStartTime` (epoch seconds) kept in the context, due = `waitStartTime + waitTime`, `waitedSeconds` in the outputs; it shall execute exactly twice for a wait that is not interrupted (arm, fire).
- `Task.reset_context_keys` shall name the context keys a reset clears (`TimerTask`: `_timer_armed_at`, `_timer_due_at`; `WaitTask` adds `waitStartTime`); the reset paths wire it in slice 4b.
- `TaskResult` shall carry `scheduled_time: int | None`; `merge_outputs` and `TaskResultBuilder.build` shall preserve every field (`target_stage_ref_id`, `scheduled_time`).
- `process_result` shall copy `result.scheduled_time` into `stage.scheduled_time` for a RUNNING result and clear it otherwise; both backends' stage UPDATE statements shall write `scheduled_time`.

- If a store call inside `StartStageHandler` or `CompleteStageHandler` fails with a store-unavailable error (connection loss, pool exhaustion, SQLSTATE classes 08 and 58, 53300, 57P01-57P03, 25006, 08007, 40003, 0A000, `OperationalError`/`InterfaceError`/pool timeouts by class, `ConcurrencyError`), then the handler shall re-raise it so the message is redelivered, and shall not record a planning failure or move the stage to TERMINAL (B02); `stabilize.errors.is_store_unavailable` shall be the one predicate, shared with the held-result path.
- `is_transient` shall classify PostgreSQL SQLSTATEs 40001, 40P01, 55P03, 53300, 57P03, 08001 and 08004 as transient in addition to the 0.33 type and name rules; 57P01, 57P02 and 57014 only when `STABILIZE_RETRY_ON_SHUTDOWN` is set; an unknown SQLSTATE shall be neither transient nor permanent (B30).

Synthesis notes recorded while building 7a:

### WI-7 slice 7b: the store-retry budget (done)
- `queue_messages` and `queue_messages_dlq` (and every custom queue table pair) shall carry `store_retries INTEGER NOT NULL DEFAULT 0` and `store_retry_since TIMESTAMPTZ` (SQLite TEXT), added by migration `01M68PK3W1DW3T8GZ3YKE3SVSJ_redelivery_budget.sql` on PostgreSQL and on SQLite by the same per-file step that adds the tenant column; `mg-queue-table` shall create the pair in that shape and the column catalog shall list both.
- `Queue.reschedule(message, delay, store_unavailable=)` shall, for a store outage, add one to `store_retries` and set `store_retry_since` when it is NULL; for any other failure it shall reset both; `Message.store_retries` shall carry the count on delivery.
- While `store_retry_since` is set and younger than the queue's `store_retry_budget` (30 minutes by default), the message shall stay deliverable past `max_attempts`; `next_ready_in` shall count it; the sweep shall move a message at or past `max_attempts` to the dead-letter queue only once its budget, if any, is spent, with the cause `store_unavailable_budget_exhausted` when a budget was open and `Exceeded max_attempts` otherwise; a message below `max_attempts` shall never be swept (B02).
- The processor shall reschedule a store-unavailable failure after `retry_delay` doubled per `store_retries`, capped at five minutes, and shall never move the stage to TERMINAL for it.

Synthesis notes recorded while building 7b:
- The plan's sweep predicate dead-lettered a spent budget whatever the attempt count; the first green run showed a message with one attempt and a spent 1-second budget being swept while the poll still delivered it. The budget is an extension past `max_attempts`, not a shorter fuse: the sweep now requires both `attempts >= max_attempts` and a spent (or absent) budget, and the cause names the budget when one was open.
- A store-unavailable reschedule adds one to `store_retries` and stamps `store_retry_since` once; any other reschedule resets both, so the next failure of a different kind falls back to the attempt rule at once.
- `Message.store_retries` is delivery metadata (set at poll, excluded from payloads like `attempts`). The processor's delay is `retry_delay * 2**store_retries`, capped at five minutes (`queue/processor/redelivery.py`), on both the threaded and the synchronous path.
- SQLite adds the columns on open through `queue/sqlite/schema.py::ensure_redelivery_columns`, the same mechanism the tenant column uses, so custom queue pairs in old files are covered; PostgreSQL custom pairs are covered by `mg-queue-table` (`LIKE queue_messages INCLUDING ALL`) and by the schema check naming the missing DDL.

## TECHNICAL PROBLEMS
1. Row ownership under one shared schema: a tenant key every engine row carries and every statement filters on.
2. A mode the engine can trust: where the schema records single vs tenancy, how the engine reads it without a policy in the way, and what it refuses.
3. Construction-time agreement: parts (store, queue, event store, processor) built with different tenants must not work together.
4. Hosts that upgrade code before schema: a clear refusal that names `stabilize mg-up`, never a silent default.

## SOLUTION DOMAINS
- Multi-tenant row keys -> PostgreSQL RLS manual (`current_setting`, `set_config(..., true)`), Casebound's and Provenance's existing policies; engine column `stabilize_tenant` so a host policy can reference it.
- Mode record -> singleton table with `CHECK (id = 1)` (SQL standard); un-policed by contract so a plain SELECT answers under any role.
- Constructor contracts -> existing stabilize pattern (`release_pool_once`, `with_schema`), `StabilizeError` hierarchy.
- Migrations -> migretti (house tool); additive column with a constant default is metadata-only on PostgreSQL 11+.

## ALTERNATIVES
- Tenant key: engine column `stabilize_tenant` [CHOSEN] vs schema-per-tenant [REJECTED: Casebound and Provenance run RLS in one schema; a schema per tenant multiplies migrations and pools] vs host-owned column only [REJECTED: the engine cannot filter on a column it does not know].
- Mode storage: singleton table [CHOSEN] vs a GUC or `ALTER DATABASE` setting [REJECTED: not visible to a plain SELECT on SQLite, not transactional, not in the migration history] vs per-process flag [REJECTED: two processes could disagree about one schema].
- Mode default when the row is missing: refuse [CHOSEN] vs default to single [REJECTED: a deleted or unreadable row would silently admit cross-tenant reads].
- Enabling tenancy: only on an empty schema (D2) [CHOSEN] vs live conversion with backfill [REJECTED for 0.34.0: no owner for rows written before the mode flipped; a later release].
- Mode read cadence: throttled re-read every 5 s per part on the borrowed connection [CHOSEN] vs once at construction [REJECTED: a mode flip under a running process would go unseen] vs every transaction [REJECTED: one extra round trip per transaction].
- Where the first mode read happens: at first engine borrow [CHOSEN, 2026-10-31] vs in the constructor [REJECTED after the live run: a constructor borrow runs the host's `on_borrow` hook outside any request (Casebound's hook reads a request contextvar and would raise), breaks `is_healthy()` on an unreachable database, and failed 9 pinned tests (`test_queue_pool_holder`, `test_pool_hooks`, `test_pool_options_and_lifetime`)]. The processor still fails fast: `QueueProcessor.__init__` hydrates its deduplicator through the store, which is a borrow.
